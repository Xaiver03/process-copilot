# Process Sentinel Online AI Demo Implementation Plan

> **For Codex:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 将序安 Process Sentinel 从“预计算事件模板 + 前端关键词回答”升级为可现场验证的“逐样本在线工业模型推理 + 服务端真实 LLM 协同研判 + 最小 AI 运行管理页”，并保持模板降级、人工确认、只读控制边界和完整审计。

**Architecture:** 采用混合 AI 架构。worker 读取不含故障标签的 52 维 TEP 回放样本，逐样本调用 PCA T²/SPE 在线监测器，在异常锁存后调用 HGB 分类器刷新故障候选与 Top-3 变量证据；FastAPI 通过 PostgreSQL 持久化推理状态并用 SSE 推送。LLM 只在服务端读取结构化事件摘要，负责解释、追问和检查顺序改写；任何超时、失联或结构校验失败都回退到确定性模板，不能修改工业模型结论或生成控制命令。

**Tech Stack:** Python 3.12、FastAPI、SQLAlchemy、PostgreSQL、scikit-learn、PyArrow、joblib、httpx、Next.js 15、React 19、TypeScript、SSE、Vitest、Pytest、Playwright、Docker Compose、Caddy。

## 1. 现状事实

当前系统已经具备 FastAPI、PostgreSQL、登录、回放、事件、人工决策、审计、Next.js 前端、Docker Compose 和公网反向代理。

当前“AI”有两条尚未接通的边界：

1. `services/ml/process_copilot_ml/model.py` 已有逐样本 `OnlinePCAMonitor`，但 `apps/api/process_copilot_api/worker.py` 只检查产物是否存在，没有调用模型。
2. `apps/web/src/lib/event-copilot.ts` 目前根据关键词返回固定文本，没有调用服务端语言模型。

当前 API 在创建 run 时直接写入 `event-template.json` 对应的事件。因此公网演示能够稳定运行，但评委看到的是模型离线构建结果，不是运行时逐样本推理。

## 2. 三种方案与推荐结论

| 方案 | 内容 | 优点 | 代价与问题 | 结论 |
|---|---|---|---|---|
| A. 只把预计算结果做得更像 AI | 保留现状，增加模型动画和说明 | 最稳、最省时间 | 仍无法证明运行时真的调用模型；自由问答仍是规则 | 不采用 |
| B. 在线工业模型 + 服务端 LLM + 模板降级 | worker 真正逐样本推理，LLM 解释事件，后台展示运行状态 | AI 可见、可问、可验证；网络失败仍能演示 | 需要改 worker、SSE、事件生命周期和前端 | **推荐** |
| C. 直接做 Agent 自动调 PLC/DCS | 增加动作规划和控制写回 | 叙事最激进 | Demo 没有真实联锁、权限和控制系统，安全与可信度不足 | 本轮禁止 |

本计划采用方案 B。当前 Demo 继续保持只读；“受控写回”只展示动作草案、校验步骤和人工门，不发送控制命令。

## 3. 目标运行链路

```text
TEP telemetry.parquet（不读取 faultOnsetSample / activeFaultId）
  -> worker 逐样本读取 52 个过程变量
  -> 数据质量门
  -> PCA T² / SPE / anomalyScore
  -> 持续性 + 滞回状态机
  -> PostgreSQL 推理消息表
  -> SSE 推送实时样本、模型耗时和告警状态
  -> 异常锁存：创建事件 + 初始候选 + Top-3 证据
  -> 再积累 20 个样本
  -> HGB 刷新候选概率和证据
  -> 操作员打开事件并自由提问
  -> FastAPI ExplanationEnhancer
       -> OpenAI-compatible LLM（成功时 mode=llm_enhanced）
       -> 确定性模板（禁用/超时/失败时 mode=template）
  -> 人工确认 / 驳回 / 升级
  -> 审计记录
```

## 4. 不可突破的产品与安全边界

- 在线模型不得读取 `faultOnsetSample`、文件名中的 fault ID、`activeFaultId` 或事件模板作为推理输入。
- LLM 不得修改异常分数、检测样本、故障候选概率、Top-3 证据、模型版本或严重等级。
- LLM 不得返回 PLC/DCS 地址、寄存器、控制指令或可直接执行的函数调用。
- 浏览器永远不能获得 Provider API Key。
- 公网 `/events/{id}/ask` 必须登录；至少 `operator` 角色才能调用，以限制成本和滥用。
- AI 管理页只向 `shift_lead` 开放。本轮只展示运行配置和测试连接，不在浏览器编辑或回显密钥。
- 所有 LLM 输出必须标记 `llm_enhanced`、`template` 或 `degraded`，禁止静默混用。
- LLM 失联不能影响工业模型、回放、事件、人工确认和审计主链路。
- 当前 release 继续支持 `INFERENCE_MODE=template` 回退，不让在线 worker 成为单点阻断。

## 5. Definition of Done

只有同时满足以下条件才允许部署：

- 回放开始后，服务器端 `currentSample` 持续推进，刷新页面后进度不丢失。
- 每个 run 明确返回 `inferenceMode=online|template` 和实际 `modelVersion`；前端不得根据是否收到 SSE 自行猜测模式。
- SSE 能看到真实 `t2`、`spe`、`anomalyScore`、推理耗时、模型版本和状态变化。
- worker 使用原始 52 个变量重新计算，不能读取冻结的 `anomalyScore` 和候选列作为输入。
- 异常事件只在在线状态机锁存后出现，而不是在 `POST /runs` 时提前生成。
- 诊断候选在锁存后第 20 个样本刷新，UI 明确区分“首次发现”和“候选更新”。
- 任意自由问题实际到达 FastAPI；LLM 在线时响应 `llm_enhanced`，断网测试时响应 `template`。
- AI 运行管理页显示工业模型、LLM、worker、数据 buildHash、最近调用耗时及降级原因。
- API Key 不出现在 HTML、Next.js bundle、API 响应、日志、截图或 Git diff 中。
- ML、API、Web、契约、infra、Compose、端到端 smoke 和 1440/1024/768/390 Playwright 全部通过。
- 公网真实浏览器完成：创建回放 -> 在线分数推进 -> 事件出现 -> 自由提问 -> 人工确认 -> 审计记录。
- 模拟“服务端已创建 run、客户端未收到响应”后，用同一个 operation-level `Idempotency-Key` 重试只能恢复原 run，不能产生孤儿或重复 run。
- 回滚演练通过：关闭 LLM 后主链路可用；切回上一 release 后公网恢复。

## 10. 已知基线风险

- `make test` 的 ML 命令遗漏 `--extra test`；Task 0 修复。
- ML fixture 使用相邻 FDE 目录推导源 ZIP，全球 worktree 中会得到错误路径；Task 0 增加 `TEP_SOURCE_ZIP`。
- 当前 create-run 立即写事件模板，必须在 online 模式下移除；Task 6 处理。
- 当前 SSE 先一次性发送已存在事件，不能表达实时推理；Task 6 改为数据库游标流。
- 当前 worker 没有队列和租约；本计划先支持单 worker、可重建状态。多 worker 分布式抢占不进入黑客松范围。
- 当前 create 请求在“服务端提交成功但响应丢失”时可能产生孤儿 run；Task 10 用浏览器会话级稳定幂等键关闭该风险。
- 当前服务没有完整迁移框架。本轮只新增表，不修改既有表字段；赛后进入多租户前再引入 Alembic。
- 外部 LLM 凭据是部署依赖。无凭据时仍可完成在线工业模型演示，但公网问答会明确显示 template 模式，不能宣称实时大模型增强。

## 11. 计划批准后的启动方式

批准后使用 `subagent-driven-development` 在本 Goal 中实施：W1/W2 的无冲突任务并行，父 Agent 在每个波次后做代码审阅、全量测试和逐提交集成。任何 P0/P1、数据泄漏、标签泄漏、密钥暴露或在线/静态数据混用都立即停止发布。
