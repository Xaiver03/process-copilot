# 连续化工过程偏移副驾驶方案设计 v01

状态：`DRAFT`  
用途：方案审批，不作为已授权实施或部署的证明

## 1. 产品定义

### 服务对象

连续生产装置的中控室当班工程师。

### 关键动作

过程出现偏移后，在 60 秒内确认优先检查的 3 个变量、最可能的故障类型、是否通知现场，以及是否暂缓当前批次。

### 目标损耗

减少工艺偏移未及时发现导致的不合格批次、返工、额外能耗和非计划停车。

### Demo 唯一主链路

```text
选择故障场景并启动回放
-> 52 路过程变量持续进入
-> 系统发现偏移并标记首次越界时刻
-> 展示最可能故障和 Top-3 变量证据
-> 生成检查顺序、风险和建议动作
-> 操作员确认、驳回或升级，并形成审计记录
```

## 2. 三种实现路线

### 路线 A：模块化单体，推荐

- Web：Next.js + TypeScript。
- API：FastAPI + Python。
- 数据：Parquet 保存时序，PostgreSQL 保存业务状态和审计记录。
- 推送：SSE 负责单向数据回放，REST 负责控制与确认。
- 部署：Docker Compose 单机部署，Nginx/Caddy 提供 HTTPS。

优点是模型生态、前端交互和部署稳定性兼顾，边界清晰；代价是需要维护 Node 与 Python 两个运行时。

### 路线 B：TypeScript 主应用 + Python 模型进程

业务接口集中在 Next.js，Python 只负责模型推理。前端开发快，但数据契约横跨两个进程，现场故障定位不如路线 A 直接。

### 路线 C：Python 一体化

FastAPI 同时提供接口和静态页面。搭建最快，但高质量工业驾驶舱、复杂图表状态和后续产品化空间不足，只适合作为失败后的极简保底。

## 3. 推荐系统结构

```text
Browser
  | REST + SSE
Next.js Web
  | typed OpenAPI client
FastAPI API
  |-- Replay Service
  |-- Detection / Diagnosis Service
  |-- Explanation Service
  |-- Action Recommendation Service
  |-- Audit Service
  |
  |-- Parquet: 原始、标准化、推理结果和场景快照
  |-- PostgreSQL: 用户、回放、事件、建议、确认与审计
  `-- Model Artifacts: scaler、PCA、分类器和版本清单
```

首版不引入 Kafka、Kubernetes、独立向量数据库或多微服务。Redis 只有在需要跨进程任务队列时才加入，不作为默认依赖。

## 4. 数据基座

### 分层

1. `raw`：原始 TEP 文件和许可证，保持只读。
2. `normalized`：统一列名、变量描述、单位、故障编号、样本序号和相对时间。
3. `features`：标准化参数、窗口特征和模型输入。
4. `predictions`：异常分数、故障概率、Top-3 变量贡献和模型版本。
5. `demo-scenarios`：为现场演示冻结的场景、回放速度和期望关键时刻。

大体量时序不逐点写入 PostgreSQL。PostgreSQL 只记录回放实例、异常事件、处置建议、人工决策和审计轨迹。

解析器必须处理一个已核验的结构例外：故障训练文件通常为 `480 × 52`，测试文件为 `960 × 52`，但正常训练 `d00.dat` 实际为 `52 × 500`，必须转置为 `500 × 52`。该规则需要 golden test，禁止通过猜测方向静默读入。

原始数据每 180 秒一个记录点。首版使用 20 点（60 分钟）窗口、stride 1；所有窗口按单条 run 切分，禁止跨 run 或随机打散相邻窗口造成泄漏。页面展示相对时间，不冒充真实生产时间戳。

### 首版模型

- 异常发现：PCA Hotelling T² + SPE/Q，使用正常工况建立基线。
- 故障研判：窗口统计特征 + HistGradientBoosting 输出正常/故障 Top-3 概率，避免引入额外的本地编译依赖。
- 变量解释：基于重构残差或标准化贡献给出 Top-3 变量，不让大模型猜根因。
- 建议生成：结构化规则模板为必备路径；配置 LLM 时只负责改写，不改变计算结论。无密钥或超时自动退回模板。

### 数据诚实性

TEP 是连续化工过程仿真。页面、作品说明和演示口播都必须显示“公开仿真数据”，不得表述为贵州磷化工真实生产数据。

## 5. 前端产品结构

### Design Read

企业工业控制场景的桌面 Web 工作台，面向当班工程师和评委，采用 Wuno Cold Light、可信、克制、高数据密度的语言。

- `DESIGN_VARIANCE: 3`
- `MOTION_INTENSITY: 2`
- `VISUAL_DENSITY: 8`

Taste skill 只用于消除模板感、统一图形语言和控制动效；数据表、趋势图和操作路径服从工业产品可用性。

### 核心路由

- `/demo`：一键进入冻结场景，比赛主入口。
- `/overview`：装置、数据新鲜度、偏移状态与待研判事件。
- `/replay`：52 路变量热力总览、回放控制、选中变量趋势和异常时间线。
- `/events`：偏移事件列表、筛选和事件预览。
- `/events/:id`：故障研判、Top-3 证据、建议动作和人工确认。
- `/records/:id`：证据快照、人工决定、模型版本和审计时间线。
- `/system`：数据来源、许可、模型版本、健康状态和真实 POC 接入说明。

比赛现场只需要走 `/demo -> /replay -> /events/:id -> /records/:id`。

### 视觉继承

- 继承 WunoOS 的 240px 应用侧栏、冷白画布、白色面板、细边框和 12/16px 圆角层级。
- 核心色沿用 `#24839B / #3996AE / #13C2C2`，不采纳工具生成的另一套主色。
- 正常、警告、故障同时使用文字、图标和线型，不只依赖绿黄红。
- 数字使用等宽或 tabular figures；中文主体继续使用 Noto Sans SC / PingFang SC。
- 动效只服务数据回放、异常出现和人工确认，支持 reduced motion。
- 52 路变量使用热力图总览，证据使用共享横轴的 3 条小多图；禁止把 52 条曲线叠成一张图。

## 7. API 与核心实体

### 核心实体

`DatasetVersion`、`ModelVersion`、`Scenario`、`ReplayRun`、`TelemetryPoint`、`AnomalyEvent`、`Diagnosis`、`EvidenceItem`、`ActionRecommendation`、`OperatorDecision`、`AuditEntry`。

### 最小 API

- `GET /healthz`
- `GET /readyz`
- `GET /api/scenarios`
- `POST /api/runs`
- `POST /api/runs/{id}/play|pause|seek`
- `GET /api/runs/{id}/stream`
- `GET /api/runs/{id}/events`
- `GET /api/events/{id}`
- `POST /api/events/{id}/decision`
- `GET /api/audit`
- `GET /api/about-data`

OpenAPI 是前后端唯一契约，前端类型由契约生成，禁止手写两套重复 DTO。

统一错误响应为 `code / message / details / trace_id`；写入接口支持 `Idempotency-Key`。SSE 必须提供心跳、断线重连和 `Last-Event-ID`，首版不引入 WebSocket。

## 8. 部署与安全

- 单台 Linux 服务器运行 Docker Compose。
- 只暴露 80/443；数据库不映射公网端口。
- Demo 使用只读公开数据，不上传企业资料。
- 管理和写入操作需要短期演示凭证；公开展示入口只能创建隔离的演示回放。
- 容器健康检查、日志轮转、资源限制和一键回滚均写入部署定义。
- 不向大模型发送完整 52 路原始数据，只发送结构化诊断摘要；无 LLM 也能完成主链路。

服务器候选与最终选择等待 SSH 只读审计结果补充。

## 10. 分阶段验收

### G0：方案批准

确认公开方式、技术路线、页面范围和服务器。

### G1：数据基座可复现

一条命令从原始 ZIP 生成标准化数据、模型、推理结果和冻结场景。

### G2：主链路本地跑通

从开始回放到人工确认全程可用，大模型离线时仍能完成。

### G3：现场稳定性

连续重复演示 5 次无致命错误；网络断开或 LLM 超时有清晰降级。

### G4：服务器发布

HTTPS 可访问，健康检查正常，数据库不暴露，能够回滚到上一镜像。
